## v0.1.0-beta の公開前確認

v0.1.0-beta を公開する前に行った確認の記録です。

### Uka サンプルの軽量化

測定方法：Release 版を同じ条件（ウィンドウ 384×682・96dpi 換算、物理 ON、待機モーション）で起動し、20 秒後に測りました。プロセスのメモリは `Get-Process`（PrivateMemorySize64、WorkingSet64）、GPU のメモリは性能カウンターの `\GPU Process Memory(pid_*)\Dedicated Usage` と `Shared Usage`、GPU の負荷は `\GPU Engine(pid_*_engtype_3D)\Utilization Percentage` です。CPU と FPS はランタイムのログの値です。環境は Windows 11、Intel UHD Graphics（内蔵 GPU）、画面の拡大率 150% です。

| テクスチャ | ファイル（tex） | private | working set | GPU 共有メモリ | CPU（1 コア比）30／60／120fps | GPU 3D 30／60／120fps |
|---|---|---|---|---|---|---|
| 4096×4096（公式のまま） | 81.3MB（10 枚） | 1,397MB | 1,406MB | 1,333MB | 5.6％／14.8％／18.8％ | 7.4％／14.9％／27.4％ |
| **2048×2048（採用）** | 15.9MB（使う 9 枚では 12.9MB） | **432MB** | 442MB | 367MB | 6.4％／13.4％／14.1％ | 7.3％／14.7％／27.7％ |
| 1024×1024（比較） | 4.1MB | 190MB | 201MB | 取得できず | —／11.8％／— | —／14.7％／— |

- 内蔵 GPU には専用メモリがないため、テクスチャはすべて共有メモリ（＝プロセスのメモリ）に置かれます。テクスチャ以外（モデル、物理、描画バッファなど）はおよそ 150MB です。テクスチャ 1 枚あたりのメモリは、計算上の大きさ（ミップマップ込み）の約 1.7 倍でした。ドライバーの割り当て方によるものとみられます。
- CPU 側の画像のコピーは、GPU への転送後に解放していることをコードで確認しました。
- 見た目：通常の表示倍率では 4096 と 2048 の違いは分かりません。顔を 3.5 倍に拡大しても、ほぼ同じでした。1024 は、拡大すると目のふちと耳の毛が少しぼやけます。アルファを使う顔のパーツ（FP.png）に縁の黒ずみはありません。
- 2048 を標準にしました。メモリは 69% 減、NAR は 85.6MB から 17.0MB になります。CPU と GPU の負荷は悪化していません。
- 縮小は `uka3d_texresize`（stb_image_resize2）で行います。sRGB を考慮し、アルファで色を重み付けして縮小します。Uka のテクスチャはすべて色の画像で、法線マップなどはありません。公式のデータは変更せず、組み立て時に縮小したファイルを作ります。

### 実機確認（SSP 2.9.33、プロファイルを空にした SSP の複製）

マウス操作は、OS の入力経路（SendInput）を通した**自動操作**です。人の手による操作ではありません。

| 項目 | 結果 |
|---|---|
| NAR の新規インストール | `--install` で展開・起動。挨拶モーション、テクスチャ 9 枚の読み込み、バルーン表示 |
| クリック・ダブルクリック | 顔のクリックで `OnMouseClick`（Face）1 回。胴のダブルクリックで `OnMouseDoubleClick`（Body）1 回、メニュー表示 |
| なで | 頭頂を片道 0.3 秒で往復して `OnUk3dPet`（Head）、クリックは出ない |
| 長押しドラッグ | 開始・終了が 1 回ずつ、ウィンドウが 160px 追従 |
| モーションの切り替え | メニューのうなずき・あいさつ・笑顔・表情を戻す・待機がそれぞれ反映 |
| 歩行・着席・追従 | 歩行（速度 270px/s）、手前の窓に着席、窓を 30 回動かして合計の移動量が一致（遅れは最大 1px）、立ち上がり |
| 2 画面（150% と 125%） | メニューから別の画面へ歩くと 480×853 に、戻ると 576×1024 に変わる |

### 未確認・既知の制限

- 人の手による操作感（なでの感触、ドラッグの手触り）
- SSTP で送った `\![change,ghost,…]` による切り替えは実行されなかった（SSP の仕様とみられる）。人が使うメニューからの切り替えは確認済み
- 2 体のゴーストを同時に開いているとき、SSTP の NOTIFY が別のゴーストに届くことがある（試験用の操作の問題で、ゴーストの動作ではない）
- Windows 10、ほかの GPU、VC++ ランタイムのない Windows、上下や 3 画面以上の画面配置、里々からの利用
- 上の確認は Visual Studio 2026 Insiders（プレビュー版）でビルドしたバイナリで行った。公開用のバイナリは安定版（Build Tools 2026 18.11）でビルドし直し、全自動テスト、NAR の新規インストールと起動・終了を確認した
- 以前の SSP 初回起動時の問題（別のゴーストが起動）は、その後 8 回と今回の試験で再現していない

## 品質改善の検証（リリース候補の前）

main へ統合する前の確認です。新機能は加えず、見つかった不具合だけを直しました。

### 修正したこと

| 不具合 | 修正 |
|---|---|
| 3D ランタイム（`ukagaka3d.exe`）が VC++ 再頒布可能パッケージの DLL（MSVCP140、VCRUNTIME140、VCRUNTIME140_1、MSVCP140_ATOMIC_WAIT）に依存し、入っていない PC では起動できない | 依存ライブラリ（libmmd、Bullet）を含めて MSVC ランタイムを静的リンクに変更。依存は OS 標準の DLL だけになった（`dumpbin /dependents` で確認） |
| NAR の中のフォルダの区切りが `\`（Windows PowerShell 5.1 の `Compress-Archive` の動作）。ZIP の仕様では `/` で、展開するツールによってはフォルダ構造が崩れる | `package-ghost.ps1` で区切りを `/` にして書き込む。作者向けの配布手順も同じ方法に変更 |
| 頭をなでても `OnUk3dPet` が出ない。髪の隙間などの透明ピクセルをカーソルが通るたびにクリック透過が一瞬オンになり、Windows がそれを「マウスが離れた」と扱って計測がやり直しになっていた | カーソルが透明ピクセルに 80ms 以上とどまってからクリック透過にする |
| ゆっくりなでると成立しない（サンプルの `windowMs` 850 では片道 0.4 秒を超えると成立しない） | サンプルの `windowMs` を 1400 に変更 |
| サンプルの当たり判定に首・腰・膝のすき間があり、腰のダブルクリックの部位名が空になる | `hit-regions.json` に胴（`上半身`）と首の球を追加し、太ももの球を広げた |
| モーション生成で、つま先のボーン名が `足先EX` 以外（例：`つま先EX`）のモデルでは足の長さを短く見積もり、歩行の蹴り出しでつま先が床に潜る（Gene で脚の長さの 5%） | 足首ボーンの子孫に付いた頂点をすべて足として扱う。Gene で 0.4% に減少。ほかのモデルの結果は変わらない |

### 検証結果

| 項目 | 結果 |
|---|---|
| 1. SSP の初回起動で既定ゴーストが出た件 | SSP の起動を 8 回試行（使用済みのフォルダ、新しいフォルダ、組み立て直後、同名ゴーストのない親フォルダ）。すべて指定のゴーストが 0.6〜1.0 秒で起動し、再現しなかった。失敗した回は SAORI とランタイムのログも SSP の起動記録（`realize2.txt`）も残っておらず、SSP がこのゴーストを読み込む前に既定のゴーストを選んでいた。NAR と起動処理に原因を示すものは見つかっていないが、原因は特定できていない |
| 2. マウス操作 | OS の入力経路（SendInput）でカーソルを実際に動かして確認。顔のクリックは `OnMouseClick`（Face）1 回。胴のダブルクリックは `OnMouseDoubleClick`（Body）1 回で、単クリックとの重複なし。長押しドラッグは開始・終了が 1 回ずつで、窓が 200px 追従。短い押し移動ではクリックもドラッグも出ない。頭頂のなでは片道 0.15〜0.7 秒の往復で `OnUk3dPet` が 1 回（長く続けるとクールダウン後に再度）。右クリックで SSP のメニュー。透明部分は下の窓に透過。顔の高さで横になでると、内側の Face と外側の Head をまたぐため成立しない（部位が変わるとやり直す仕様のとおり） |
| 3. DPI の異なる 2 画面（150% と 125%） | 歩行で画面をまたぐと、3D ウィンドウが 576×1023 から 480×853 に変わる（144:120 の比）。着席の高さ（窓の上端から 3D ウィンドウ上端まで）は 570px と 475px で同じ比。着席中に対象の窓を画面間で往復させても追従し、境目をまたぐ窓では見えている側の上端に座る。SSP のメニューから「別の画面へ歩く」で移動し、バルーンも移動先に表示 |
| 4. Uka 以外のモデル | ユーザー提供の実モデル 5 体（同じ作者の衣装違い。リポジトリには含めない）と、CG-CA の Gene（CC BY 4.0、224 ボーン。検証用に手元へ取得しただけで、リポジトリや配布物には含めない）でモーションを生成。歩行の足の滑りは平均 0.76〜0.88%、床より下の頂点は脚の長さの 0.4% 以下、待機の足のずれは 0。4 体を描画して、待機・歩行・着席・つまみの姿勢が破綻しないこと、マントが物理で追従することを確認 |
| 5. スキニングの形式 | 合成モデルで BDEF1／BDEF2／BDEF4／SDEF／QDEF と、不正な SDEF のフォールバックを libmmd と比較（既存のテスト）。実モデル 7 体（Uka、Gene と上記 5 体。Gene は BDEF4 が 4,916 頂点）でも比較し、位置の差は最大 5.7e-6。実モデルの 2 ボーン頂点を SDEF と QDEF に置き換えた版（Uka で SDEF 19,017・QDEF 9,504 頂点）でも差は同程度 |
| 6. NAR の新規導入 | 組み立てた NAR（37 ファイル、85.6MB）を、プロファイルを空にした SSP の複製に `--install` で導入。展開・起動・テクスチャ 9 枚の読み込み・終了（終了コード 0）を確認し、警告やエラーはなし。依存 DLL は exe・SAORI・yaya.dll とも OS 標準のものだけ |
| 7. 自動テストとビルド | Debug、Release とも x64 26/26 件、x86 2/2 件が合格（静的リンクへの変更後に全体をビルドし直して確認） |
| 7. 長時間常駐 | Release 版を 60 分常駐させ、15 秒ごとに挨拶・表情・歩行・着席・対象の窓の移動・立ち上がり・うなずきを繰り返した（計 239 回、10 分ごとにモデルを読み直して計 5 回）。エラー 0、終了コード 0。1 分ごとの記録で、private メモリは 1390〜1403MB（開始 1397MB、終了 1403MB）、ハンドル 280〜285、GDI 7、USER 18〜21、スレッド 6〜9 で、増え続けるものはなかった。CPU は 1 コア比で 13〜14%（物理 ON、60fps、内蔵 GPU） |

### 未検証・残っている課題

- 人の手によるマウス操作は行っていません。クリックなどは OS の入力経路を通る合成入力で確認しました
- SSP の初回起動で別のゴーストが出た件は原因が分かっていません。再現しないため、修正もしていません
- VC++ 再頒布可能パッケージが入っていない、まっさらな Windows では起動していません。依存 DLL を調べて、OS 標準のものだけになったことを確認しました
- Uka 以外で試したモデルは、ユーザー提供の同じ骨格の衣装違いと、Uka と同じプロジェクトの Gene です。利用規約への同意が必要な配布サイトのモデル（別の作者の骨格や命名）は試していません。実際の SDEF／QDEF を使ったモデルも手元になく、変換したデータで確認しました
- Uka は 4096×4096 のテクスチャを 9 枚使うため、内蔵 GPU では約 1.4GB のメモリを使います（テクスチャだけでミップマップ込み約 770MB）。常駐試験で増加は見られませんでしたが、量としては大きいままです
- 2 画面の検証は 1 組の配置（左右に並んだ 150% と 125%）だけです。上下の配置、隙間のある配置、3 画面以上は未確認です
- 試験中に、透明部分のクリックが下にあった別のアプリのウィンドウに届いたことがありました（クリック透過としては正しい動作です）

## 品質改善：着席と負荷

機能は増やさず、着席の見た目、CPU 負荷、サンプルのモーションを直しました。仕組みは [architecture.md](architecture.md) の末尾にあります。モーションは着席・負荷の作業のあとに分けて行いました。

### 計測環境

- Windows 11 Pro、Intel UHD Graphics（内蔵 GPU）、内蔵ディスプレイ 120Hz、Release ビルド
- モデル：CG-CA Uka（頂点 49,955、ボーン 302、剛体 164）、`idle.vmd`、物理演算 ON、ウィンドウ 384×682（96dpi 換算）
- 改善前は品質改善の前の Release ビルド。同じ手順で 24 秒ずつ起動し、ランタイムの実測ログと GPU エンジン使用率のカウンターを読みました

### 負荷（改善前 → 改善後）

| 上限 | 実測 FPS | CPU（1 コア比） | 評価 1 回の平均 | GPU（3D エンジン） |
|---|---|---|---|---|
| 30 fps | 30 → 30 | 15.3% → 7.6% | 4.02ms → 1.63ms | 7.1% → 7.0% |
| 60 fps | 60 → 60 | 27.3% → 13.0% | 3.76ms → 1.34ms | 13.2% → 12.8% |
| 120 fps | 120 → 120 | 29.5% → 16.6% | 3.75ms → 1.33ms | 25.1% → 24.7% |

`uka3d_bench` で 1 tick の内訳を測ると、改善前の 4.95ms のうち約 4.45ms が libmmd の CPU スキニング（毎 tick の全頂点コピーを含む）でした。物理演算は約 0.38ms、ボーンとモーフの評価は約 0.12ms です。スキニングを自前の実装（約 0.72ms）に置き換え、libmmd にはボーンとモーフだけを計算させています。全頂点で libmmd の結果と一致することを自動テストで確認しました（Uka で最大差 3.8e-6）。GPU 負荷は変えていません。

### 着席

| 項目 | 改善前 | 改善後 |
|---|---|---|
| 座る高さ | 腰ボーンの関節を上端に合わせるため、体が約 100px 沈む | 骨盤と太ももの表面でいちばん低く見える点を上端に合わせる。Uka は `offsetY` 0.4 でショートパンツの下端が上端に乗る |
| モデルごとの調整 | 腰ボーン名と高さ補正を着席のたびに指定 | `configure_seat` と `ukagaka3d.json` の `seat` で、基準ボーン、接地ボーン、上下左右の補正、向き、角からの距離、遷移時間を設定。着席中も反映 |
| 対象の移動への追従 | 最大 11px、平均 1px の遅れ | 最大 1px、平均 0.3px（ランタイム単体、対象を 16ms ごとに 8,3px 移動） |
| 着席と立ち上がり | 姿勢とウィンドウ位置が 1 フレームで切り替わる | 姿勢をボーン単位でクロスフェードし、ウィンドウは弧を描いて移動（既定 350ms） |
| 座ったままの揺れ | 整数ピクセルへの丸めで上下に 1px 揺れることがある | 端数は投影をずらして合わせる。対象が止まっている間のウィンドウ移動は 0 回 |

### モーション

待機・歩行・着席・つまみを、モデルの脚と腕を測って作る生成器（`uka3d_motiongen`）に置き換えました。組み立て時にモデルに合わせて作るので、ほかの PMX に差し替えても使えます。データはすべて計算で作るため、配布に制約はありません。挨拶とうなずきは以前のままです。

| 項目（CG-CA Uka、同じ測り方） | 以前 | 今回 |
|---|---|---|
| 歩行：接地中の足の滑り（歩く速さに対する割合） | 平均 369%、最大 544% | 平均 0.9%（足が床を離れる瞬間の 1 サンプルだけ 45%、0.03 単位） |
| 歩行：床より下に出た頂点 | 0.20（脚の長さの 1.9%） | 0.001 |
| 待機：足のずれ／床より下 | 0.053／0.103 | 0／0 |
| 歩行の周期 | 1.0 秒（速度と無関係） | 1.5 秒。96dpi で毎秒 180px 歩くときに足が滑らない長さ |

SSP のサンプルでは、歩行速度を画面の拡大率に合わせます（150% で毎秒 270px）。実機の画面で、歩行（かかとの接地から蹴り出し）、待機、着席、つまみの姿勢を確認しました。

### 実機確認

SSP 2.9.32f と YAYA 6.8.3 で、Release 版の Uka サンプルを `--ghost` で起動しました。メニューと同じイベントを SSTP の `NOTIFY` で送り、ウィンドウ位置とログ、画面を確認しました。

| 項目 | 結果 |
|---|---|

### 未検証・残っている課題

- GPU 負荷は改善していません（4x MSAA と輪郭線の描画が大半）。内蔵 GPU で 120 fps にすると 3D エンジンを約 25% 使います
- UV モーフを持つモデルは、libmmd 側の頂点コピーが残るため CPU の改善幅が小さくなります。Uka 以外のモデルでは負荷を測っていません
- 着席の新しい処理は 1 画面（スケーリング 150%）でだけ確認しました。2 画面と DPI の異なる画面間での追従は、自動テスト以外では未確認です
- SSP 上での追従に 1 回だけ出た 10px の遅れの原因は調べていません
- 実マウスでのドラッグ（つまみ）と、つまみ中のクロスフェードの見た目は手で操作していません。自動テストでは開始と復帰を確認しています
- 対象ウィンドウの上端が画面の上端に近いときは、キャラクターを画面内に収めるため上端より下に座ります
- 生成したモーションは Uka と自動テスト用の合成モデルでだけ確認しました。ユーザー提供の実モデルやほかの PMX での見た目は未確認です
- 歩行の足が滑らないのは、サンプルと同じ 3D ウィンドウの大きさと、拡大率に合わせた速度で歩かせた場合です。`Move3DTo` に別の速度を渡すと、その比率で滑ります
- 足 IK を持つモデルでも、生成した 4 つのモーションの間は足 IK を無効にします。床が傾いている場面などは扱いません
- 挨拶とうなずきは以前の合成モーションのままです。立ち上がりは専用のモーションを作らず、着席姿勢から待機へのクロスフェードで表現しています
- 1 回目の SSP 起動で、新しいフォルダを `--ghost` に渡したのに既定のゴーストが起動したことがありました。2 回目は正しく起動しました。原因は調べていません

## Phase 0.5：FPS 制限と物理演算

### 計測環境

- Windows 11 Pro、Intel UHD Graphics（内蔵 GPU）、内蔵ディスプレイ 120Hz、Release ビルド
- モデル：ユーザー提供の実モデル A（頂点 35,016、剛体 132、ジョイント 236、マントあり）。リポジトリには含めていない
- モーション：合成の `待機テスト.vmd`（4 秒ループ）。ウィンドウサイズ 480×720
- CPU は、プロセスの CPU 時間を経過時間で割った値（1 コア比）。GPU は、パフォーマンスカウンター `\GPU Engine(pid_*engtype_3D)\Utilization Percentage` を 0.5 秒ごとに 8 回測った平均

### 実測値

| 設定 | 描画 FPS | 最大フレーム間隔 | 評価（スキニング＋物理） | 物理 tick/s | CPU（1 コア比） | GPU 3D |
|---|---|---|---|---|---|---|
| `--fps 30` 物理 ON | 30.2 | 33.9ms | 2.98ms | 59.8 | 11.6% | 6.6% |
| `--fps 30` 物理 OFF | 30.2 | 33.7ms | 2.19ms | 0 | 8.1% | 6.7% |
| `--fps 60` 物理 ON | 60.1 | 17.2ms | 2.65ms | 59.8 | 19.2% | 13.2% |
| `--fps 60` 物理 OFF | 60.1 | 16.9ms | 2.19ms | 0 | 17.3% | 13.3% |
| `--fps 120` 物理 ON | 120.0 | 14.1ms | 2.60ms（60Hz） | 59.9 | 23.3% | 23.6% |
| `--fps 120` 物理 OFF | 120.1 | 9.1ms | 2.12ms | 0 | 32.2% | 24.2% |
| `--fps unlimited` 物理 ON※ | 1308 | 6.7ms | 2.08ms（60Hz） | 59.9 | 59.2% | 未計測 |
| `--fps unlimited` 物理 OFF※ | 508 | 10.2ms | 1.73ms | 0 | 103% | 未計測 |

※ unlimited は、マントのない実モデル（剛体 68）で計測。

わかったこと：

- 30／60／120fps の指定どおりに描画されている。120Hz のモニターでは、どれも VSync 分周（`Present(4)`／`Present(2)`／`Present(1)`）が選ばれる。
- 物理の tick は、描画 FPS に関係なく約 60/s で一定。30fps でも 120fps でも、物理は速くも遅くもならない。
- 物理 ON による CPU の増加は、1 コア比で +2〜3.5%（評価 1 回あたり +0.5〜0.8ms）。GPU 負荷は物理の有無でほぼ変わらず、描画 FPS にほぼ比例する。
- 120fps では、物理 ON の方が CPU 使用率が低い。物理 ON ではスキニングを 60Hz で行い、その間は頂点を補間しているため。
- 全物理版（剛体 329、ジョイント 948）は、評価 7.1ms、60fps で CPU 47%（1 コア比）。
- Debug ビルドは評価に約 40ms かかり、約 24fps になる（Bullet と libmmd が最適化されないため）。物理の tick は 59.7/s で正しく進む。

- 対象は実モデル A の「全物理」版（マントの剛体 228、ジョイント 948、ジョイントに回転ばね 10 と回転制限）。腕を下ろすモーションで、マントが T ポーズのときの形のまま横に広がる。
- 試したこと：
  - 回転ばねを 0 にする（メモリ上だけで、モデルは変更していない）
  - T ポーズから 2 秒かけて腕を下ろすモーション
  - Bullet の既定プロファイルと MMD 2.75 互換プロファイル

  いずれも結果は変わらなかった。スリープ（非アクティブ化）は libmmd 側で無効になっている。
- 通常版の実モデル A（剛体 132）は自然に垂れる。
- **MMD 本体で同じモデルとモーションを使った比較はしていないため、原因（libmmd の再現性か、モデル側の T ポーズ前提の設計か）は未確定。** 次は MMD 本体で比べることを推奨する。
- モデルの規約で、物理が破綻し続けた状態での使用とマントの改造は禁止されているため、モデルには手を加えていない。

### 機能の詳細

### A. PMX の読み込み

- ✅ パスを指定して読み込む（`--model`）
- ✅ 頂点・面・UV・マテリアル・テクスチャ
- ✅ 日本語のファイル名とフォルダ名（ユーザー提供の実モデルの日本語フォルダ・ファイル名、`テスト用モデル\テストキャラ.pmx`、`tex\顔.png` など）
- ✅ ファイルがない、壊れているときのエラー表示（コンソール／ログ。ターミナルなしで起動したときはメッセージボックス）
- 🟡 エラー時のメッセージボックス表示（エクスプローラーからの起動）：コードの経路はあるが、手動では確認していない

### B. 3D 描画

- ✅ Direct3D 11 で描画（4x MSAA）
- ✅ モデル全体が収まる初期カメラ
- ✅ アルファ付きテクスチャ（合成モデルの光輪 TGA で確認）
- ✅ 基本的なライティング（MMD 風：アンビエント＋拡散、トゥーン、スペキュラ、スフィア、輪郭線）
- ✅ 画面を更新し続ける（Release 版・実モデルで約 120fps＝垂直同期の上限、Debug 版＋デバッグレイヤーで約 28fps。Intel UHD Graphics で測定）
- 🟡 ウィンドウのサイズ変更：通常ウィンドウの枠のドラッグ、背景透過モードの Ctrl＋ホイールとも、実装済みだが手動では確認していない（`ResizeBuffers` の処理はある）

### C. VMD モーション

- ✅ 読み込み、ボーンアニメーション、時間に応じた動き、ループ再生（ログで確認：フレームが 120 → 0 に戻る）
- ✅ VMD を指定しないときは静止表示（ユニットテストと GUI テスト）
- 🟡 再生／一時停止（Space、右クリックメニュー）：実装済みだが手動では確認していない
- ❗ ユーザー提供のモデルフォルダーには VMD がなかったため、実モデルでの確認には自作の合成 VMD を使った。市販・配布されている一般的なモーション（ダンスなど）では未検証

### D. 透過ウィンドウ

- ✅ DirectComposition でデスクトップに透過合成（黒背景を透明に見せる方式ではない）
- ✅ 透明部分のクリック透過（ログで確認：モデルの上で OFF、透明部分で ON）。透過 ON（`WS_EX_LAYERED`）の間も描画が消えないことをスクリーンショットで確認
- 🟡 ドラッグでの移動：実装済み。Claude の画面操作ツールがこのウィンドウへのドラッグを送れなかったため（ツール側が背面のエクスプローラーと判定した）、**手動での確認が必要**
- 🟡 右クリックメニュー（終了など）と Esc での終了：同じ理由で**手動での確認が必要**。WM_CLOSE による終了は確認済み

### E. ログ

- ✅ 起動と終了、PMX と VMD の読み込み結果、Direct3D の初期化結果、致命的なエラー

### 手動で確認してほしい項目

1. `ukagaka3d.exe --model <PMX> --motion <VMD>` で起動し、モデルを左ドラッグすると移動できるか
2. 右クリックメニューの「一時停止／再生」「先頭に戻す」「常に最前面」「クリック透過」「終了」が動くか
3. Space（一時停止）、Home（先頭に戻す）、Esc（終了）
4. 通常ウィンドウ（`--windowed`）で枠をドラッグしてサイズを変えられるか。背景透過モードの Ctrl＋ホイール
5. エクスプローラーから（ショートカットなどで）起動して読み込みに失敗したとき、メッセージボックスが出るか
6. 一般的な配布モーションでの再生
